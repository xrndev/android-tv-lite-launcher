# Releasing

How a version of Lite Launcher and the `tvlite` installer is published, and why it needs **your own signing key**.

## Why a release key

Until now the launcher APK is signed with a throwaway *debug* key generated by `launcher/build.sh`. Android only lets an app
be updated by an APK signed with the **same key**, so a launcher signed with a debug key can never be cleanly updated by
anyone else's build. A release key, kept secret by the maintainer, fixes that. **Never commit it** (`*.keystore` is in
`.gitignore`) and keep a backup: if you lose it, users have to uninstall the launcher to get updates.

`tvlite` copes with a signature change when it finds an older launcher already installed (it uninstalls it and installs the
new one; only the launcher's own settings, such as hidden apps and order, are lost).

## One-time setup (maintainer)

```bash
keytool -genkeypair -v -keystore litelauncher-release.keystore -alias litelauncher \
        -keyalg RSA -keysize 4096 -validity 36500
```

Choose a strong password and store the keystore somewhere safe and **outside** the repository.

For GitHub Actions, add these repository secrets (Settings -> Secrets and variables -> Actions):

| Secret | Value |
|---|---|
| `LITE_KEYSTORE_B64` | `base64 -w0 litelauncher-release.keystore` |
| `LITE_KS_PASS` | keystore password |
| `LITE_KEY_PASS` | key password (omit if the same) |
| `LITE_KEY_ALIAS` | alias, if not `litelauncher` |

## Publishing a version

1. Bump `launcher/VERSION` (`X.Y.Z`; the Android `versionCode` is `X*10000 + Y*100 + Z`) and `installer/pyproject.toml`.
2. Tag and push: `git tag vX.Y.Z && git push origin vX.Y.Z`.
3. `.github/workflows/release.yml` builds the signed APK and the Windows executable and attaches them to a GitHub Release
   together with a `SHA256SUMS` file.

> While the project is alpha, releases are published as **pre-releases** (v0.1.0 was the first, built by this workflow).

Locally (no CI): `LITE_KEYSTORE=/path/to/keystore LITE_KS_PASS=... bash launcher/release.sh`.

## Verifying a download

```bash
sha256sum -c SHA256SUMS
```

The Windows executable is **not code-signed**, so SmartScreen will warn on first run. Checking `SHA256SUMS` (or building
from source) is the way to be sure of what you run.
